# RCA — FloraSetu (deployment `flora-modular-core`) serves only the Emergent logo

## Verdict
The production deploy **succeeded on the wrong build**. The app is live-but-wrong: the pipeline built and shipped the **Emergent template scaffold**, not the real FloraSetu monorepo. This is a **template/architecture mismatch**, not a broken build — and part of it (Postgres/PostGIS + Redis) is **not supported by the Emergent deployer platform** at all.

## Evidence (from the successful run `56409c64-de25-44c2-8422-46680654db0e`)
- Deployment template = `fastapi_react_mongo_shadcn_base_image` (FastAPI + React + **MongoDB**). frontend_type = cloudflare. No manifest override exists in GCS — the build used the **stock farm template**.
- The pulled source at `/app/scratch` contains **two apps layered on top of each other**:
  - **Real app:** `/apps/api` (NestJS: `migrations/`, `seed/`, `dist/`) and `/apps/web` (Vite: `vite.config.ts`, `dist/`, `index.html`).
  - **Leftover Emergent scaffold:** `/frontend` (CRA+craco; `public/index.html` = `<title>Emergent | Fullstack App</title>`, `assets.emergent.sh/scripts/emergent-main.js`), `/backend` (FastAPI `server.py` + `requirements.txt`), and `etc/supervisor/conf.d/supervisord.conf` with `[program:backend] uvicorn server:app --port 8001`, `[program:frontend] yarn start` in `/app/frontend`, and `[program:mongodb] mongod`.
- Build logs confirm the frontend stage did `COPY frontend/ /app/` → `yarn build` → found `build/` → copied to `/frontend-output` → served at `/usr/share/nginx/html`. **It built `/frontend` (the placeholder), never `/apps/web`.**
- Runtime entrypoint reads the supervisord `[program:backend]` = `uvicorn server:app` in `/app/backend`. **The running "API" is the FastAPI stub `server.py`, not NestJS `/apps/api`.**
- The earlier `mongodb_migrate` failures (`list source databases … exit code 1`) are the template assuming a local Mongo this app doesn't have. **No Postgres/PostGIS/Redis provisioning happened — the deployer has no step for it.**

## Answers to the specific asks
**1. What did the production pipeline actually build/run?**
- Frontend: `COPY frontend/ /app/` then CRA/craco `yarn build`; publish dir `/usr/share/nginx/html`, served by nginx on **:8080** (`/api/*` → `127.0.0.1:8001`). This is the **Emergent placeholder** `/frontend`, not `/apps/web`.
- Backend: farm final image installs `/backend/requirements.txt` (Python) and runs `uvicorn server:app --host 0.0.0.0 --port 8001` from `/app/backend` — the **FastAPI stub**, not `node dist/main` from `/apps/api`.
- Datastore: MongoDB (Atlas) is what the template provisions; migration was a no-op. **Correct as you diagnosed** — it assumed `/frontend` + `/backend` (FastAPI) + Mongo.

**2. Were Postgres 15 (+PostGIS) and Redis 7 provisioned in prod?**
- **No.** The Emergent deployer provisions **MongoDB only**. There is no Postgres/PostGIS or Redis provisioning step in the pipeline and no env vars (`DATABASE_URL`, `REDIS_URL`) were wired. This is a **hard platform limitation**, not a config oversight.

**3. How should apps/api migrations/seeds run against prod Postgres?**
- **Not possible today** — there is no production Postgres to run them against, and the farm runtime image is Python-based with **no Node runtime**, so NestJS `yarn migrate` / `node dist/main` cannot execute in it. If/when an external Postgres+PostGIS is provided out-of-band, migrations would run as `cd apps/api && yarn migrate` then the seed scripts, against `DATABASE_URL` — but the deployer cannot host that today.

**4. The production manifest used**
- The **stock farm template** (no override in GCS): `Dockerfile.cloudbuild` with stages `frontend-build` (COPY `frontend/`, `yarn build`), `backend-build` (pip install `backend/requirements.txt`), `final-base`/`final-build` (nginx :8080, uvicorn :8001 via `entrypoint.sh`). This layout is fundamentally incompatible with a NestJS+Vite monorepo on Postgres/Redis.

## Why this can't be fixed with a manifest edit from the deployer side
Even a rewritten `Dockerfile.cloudbuild` that builds `/apps/web` (Vite→dist) and `/apps/api` (NestJS) would still fail in production because:
1. **No Postgres/PostGIS and no Redis can be provisioned** by the platform — the NestJS API cannot boot without them.
2. The **runtime image has no Node** — it's the Python/uvicorn farm base; `node dist/main` won't run, and `entrypoint.sh`/supervisord are hardwired to uvicorn.
3. The pulled source **still ships the scaffold `/frontend` + `/backend` + supervisord**, which shadow the real apps.

## Recommended path (E1 / user action)
- This app's architecture (NestJS + PostgreSQL 15 + PostGIS + Redis 7 + Vite monorepo) **does not match any Emergent deployment template**, and its datastores are **not supported by the Emergent deployer** (MongoDB-only). It cannot be correctly deployed on this platform as-is.
- Options to surface to the user:
  - Deploy on infrastructure that provides managed **Postgres+PostGIS + Redis** and a **Node runtime** (the app is self-contained: `apps/api` NestJS on 8001, `apps/web` Vite build served statically, `VITE_API_URL` → prod `/api`).
  - Or re-platform the app onto the supported Emergent stack (FastAPI + React + MongoDB) if staying on Emergent is required — a substantial rewrite.
- Regardless, remove the leftover scaffold (`/frontend`, `/backend`, `etc/supervisor/.../supervisord.conf`) so no template auto-build can pick up the placeholder again.

## Required env (for whatever platform hosts it)
- API: `DATABASE_URL` (postgres+postgis), `REDIS_URL`, JWT/auth secrets, `NODE_ENV=production`, `TRUST_PROXY`.
- Web (build-time): `VITE_API_URL` → production API origin with `/api` suffix.
